# テスト・検証方針

## 1. 基本方針

テスト件数やカバレッジの数値を増やすこと自体より、**入力境界、日付、テキスト取り込み、バックアップの形式検証、暗号化・復号**など、間違えると不具合が分かりにくい処理を優先する。

画面やSQLiteを利用した一連の操作は、自動単体テストとは別の手動確認で扱う。

## 2. 自動テスト

直近のローカル実行結果は**8ファイル・70テスト成功**。対象は次のとおり。

| 対象                     | 主な確認観点                                                                       |
| ------------------------ | ---------------------------------------------------------------------------------- |
| 日付ユーティリティ       | ローカル日付・年月、月範囲とUTCの変換、異常値                                      |
| テキストユーティリティ   | 要約の整形・切り詰め、カンマ区切りの解析                                           |
| テキストファイル取り込み | `.txt` / `.md`、見出し分割、空内容、ファイル数・サイズ・文字数制限                 |
| ナレッジ入力スキーマ     | 必須入力、既定値、トリム、上限境界、タグ上限                                       |
| 問い合わせ入力スキーマ   | 必須入力、各フィールドの最大長、発生日の形式、タグ上限                             |
| 分類・タグ入力スキーマ   | 名称の上限、空文字、タグ名のカンマ禁止                                             |
| 暗号化バックアップ       | 暗号化→復号、誤パスワード、改ざん、ファイル形式・バージョン                        |
| 通常バックアップ検証     | 必須テーブル、形式不正、フィールド型、アプリ識別子、件数サマリー、未知テーブル警告 |

最新のテスト結果は実行時のCIまたは`npm run test`で確認する。

## 3. 静的チェック・監査

```bash
npm ci
npm run format:check
npm run lint
npm run test
npm run build
```

GitHub Actionsでは、これらのフロントエンド品質チェックをpush / Pull Requestで実行する構成としている。Windows向けNSISのビルドは、現段階ではローカルのTauri環境で別途確認する。

追加監査：

```bash
npm audit
npx knip
cd src-tauri
cargo audit
cargo check
```

`cargo audit` の指摘件数は`Cargo.lock`全体の結果なので、対象OSやfeature、修正可能性を調べたうえで判断する。
